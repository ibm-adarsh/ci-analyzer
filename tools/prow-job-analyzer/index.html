    Workflow Reference — openshift-e2e-libvirt-vpn (IBM Z Homogeneous)

    Every IBM Z homogeneous (z-z) job runs the same openshift-e2e-libvirt-vpn workflow. It consists of three phases executed in strict order: PRE → TEST → POST. Click any step card to read a detailed explanation of what it does and why it exists.

    CI Pod (OpenShift) ──VPN──▶ bastion-z.svc (CoreDNS) ──qemu+tcp:16509──▶ IBM Z LPAR (lnxocp0X) ──virsh/libvirt──▶ VMs (control × 3 + compute × 2)
    PRE  ·  Infrastructure Setup
    🔑
    upi-libvirt-cleanup-pre
    Boskos lease acquisition · pre-flight cleanup · VPN connectivity check
    ▼
    What it does This is the first step of every job. It contacts the Boskos lease server and acquires a libvirt-s390x-vpn-quota-slice resource — a slot on one of the IBM Z LPARs (e.g. libvirt-s390x-1-2). Once the lease is granted, the step stores the slot name in LEASED_RESOURCE so all subsequent steps know which LPAR to use. It then SSH-connects through the VPN to the acquired LPAR and destroys any leftover VMs, virsh domains, storage volumes, and DNS records from previous runs. This prevents the infamous "storage volume already exists" error at install time. Why it exists IBM Z LPARs are shared physical machines, not ephemeral cloud VMs. If a previous CI run crashed mid-install without cleanup, stale virsh resources will still exist on the LPAR. Without this pre-cleanup, the next install will fail immediately. Boskos ensures only one job at a time runs on each LPAR slot. Failure means ① Boskos lease pool exhausted — all LPAR slots are busy; job queued until one frees. Check boskos-metrics ↗. ② VPN tunnel broken — CI pod cannot reach the LPAR. Check VPN pod logs in the build cluster. ③ Previous cleanup left the LPAR in a broken state. Key artifacts
    upi-libvirt-cleanup-pre/build-log.txt upi-libvirt-cleanup-pre/finished.json
    ⚙️
    upi-conf-libvirt (chain)
    install-config · ignition files · DNS · network bridge · HTTPD lease
    ▼
    What it does A chain of configuration steps that produces everything needed to boot the cluster VMs. It acquires a second Boskos lease for an HTTP server (HTTPD_POOL_NAME=httpd) that will serve RHCOS kernel/initrd/ignition files to the VMs during first boot (s390x network boot). It then generates the OpenShift install-config.yaml, runs the installer to produce ignition configs for bootstrap/master/worker nodes, sets up DNS records on the LPAR's dnsmasq for api.<cluster>.<domain> and *.apps.<cluster>.<domain>, and creates the libvirt network bridge that all VMs will share. Parameters like VOLUME_CAPACITY, DOMAIN_MEMORY, COMPUTE_COUNT are applied here to size the VMs correctly for the LPAR's resources. Why it exists IBM Z uses UPI (User Provisioned Infrastructure) — there is no cloud provider to handle networking or DHCP automatically. All network config, DNS, and ignition file hosting must be set up manually before any VM can boot. The HTTP server is needed because s390x boots over the network (no local CD/USB). Failure means DNS misconfiguration → bootstrap hangs waiting for api.<cluster>. HTTPD lease failure → VMs cannot download boot files. Installer crash → check upi-conf-libvirt/build-log.txt for FATAL lines. Key artifacts
    upi-conf-libvirt/build-log.txt upi-conf-libvirt-network/build-log.txt
    💾
    ipi-conf-etcd-on-ramfs
    Patches etcd to run on RAM-backed tmpfs — bypasses slow virsh disk I/O
    ▼
    What it does Injects a MachineConfig into the install-config that, when applied by the MCO after bootstrap, mounts a tmpfs (RAM disk) at /var/lib/etcd on all control-plane nodes. This means etcd's WAL (write-ahead log) and data directory live entirely in memory, not on the virsh virtual disk. The trigger is ETCD_DISK_SPEED=slow, which is always set for IBM Z libvirt jobs. Why it exists IBM Z virsh virtual disks have high latency compared to NVMe SSDs. etcd has strict fsync latency requirements — if writes exceed ~10ms consistently, etcd leader elections fail and the cluster becomes unstable or fails to bootstrap entirely. Moving etcd to RAM eliminates this constraint. The tradeoff is that etcd data is lost on VM reboot, but in CI that doesn't matter. Failure means If this step fails, the MachineConfig will not be injected. The cluster will still attempt to install but etcd will likely time out during bootstrap, showing "waiting for etcd" in the install log. Check ipi-conf-etcd-on-ramfs/build-log.txt for MachineConfig rendering errors. Key artifacts
    ipi-conf-etcd-on-ramfs/build-log.txt
    🏗️
    upi-install-libvirt
    Most critical step — creates VMs, bootstraps OCP, waits for cluster ready
    ▼
    What it does This is the longest and most failure-prone step. It uses virsh (via qemu+tcp://lnxocp0X:16509/system) to create all VMs — 1 bootstrap, 3 control-plane, and 2+ compute nodes — each with the specified DOMAIN_MEMORY and DOMAIN_VCPUS. VMs boot over the network from the HTTPD server (s390x network boot), download ignition configs, and join the cluster. The step then runs openshift-install wait-for bootstrap-complete (waits up to 30 min for bootstrap), then wait-for install-complete (waits up to 40 min for all cluster operators to become available). Once done, it destroys the bootstrap VM. At the end it approves pending CSRs so worker nodes can join. Why it exists Standard OpenShift UPI install flow, adapted for IBM Z. There is no cloud provider automation — every VM creation, network attachment, and node join is scripted explicitly. The two-phase wait (bootstrap → install) is the standard OCP install contract. Failure means Most job failures originate here. Common causes:
    ① "storage volume already exists" → pre-cleanup failed, stale VMs remain.
    ② "timed out waiting for bootstrap" → bootstrap VM can't pull images (registry outage) or etcd fails (check etcd-on-ramfs step ran).
    ③ "timed out waiting for install" → a cluster operator is degraded. Check .openshift_install.log for the specific operator.
    ④ CSR approval hanging → worker VMs booted but CSRs weren't auto-approved.     Key artifacts
    upi-install-libvirt/build-log.txt upi-install-libvirt/.openshift_install.log ⚑ upi-install-libvirt/bootstrap.ign (generated)
    🐛
    ipi-conf-debug-kdump-configure-logs
    Enables kdump + journal forwarding for crash diagnostics
    ▼
    What it does Applies MachineConfigs to all nodes that enable kdump (kernel crash dump), configure systemd-journald to forward logs to the cluster logging stack, and set extended kernel log levels for debugging. This runs after install completes so the cluster is already up when these MachineConfigs are applied. Why it exists If a node kernel panics during testing, kdump captures a vmcore that can be analysed post-hoc. Without this, node crashes leave no forensic evidence and look like unexplained test failures. Failure means Usually non-fatal for the overall job. A failure here means kdump/journal configs were not applied but testing can proceed. Check ipi-conf-debug-kdump-configure-logs/build-log.txt for MachineConfig application errors or MCO rollout timeouts. Key artifacts
    ipi-conf-debug-kdump-configure-logs/build-log.txt
    TEST  ·  Workload Execution
    📋
    openshift-e2e-libvirt-conf
    Configures the test runner — selects suite, sets skip list, upgrade params
    ▼
    What it does Writes a test configuration file that controls what openshift-tests will run. It sets TEST_SUITE (e.g. openshift/conformance/parallel or openshift/conformance/serial), generates the TEST_SKIPS list (s390x-specific tests that are known to fail or not apply), and for upgrade jobs sets UPGRADE_FROM/UPGRADE_TO versions and configures the upgrade test runner. Why it exists IBM Z has a longer skip list than x86 — some Kubernetes conformance tests use x86-specific features (SIMD, certain CSI drivers, GPU tests). This step centralises all that s390x-specific knowledge so it doesn't have to be repeated in every test step. Failure means If this step fails, the actual test step will not run (it depends on the config file). Check openshift-e2e-libvirt-conf/build-log.txt for config generation errors. Key artifacts
    openshift-e2e-libvirt-conf/build-log.txt
    🧪
    openshift-e2e-libvirt-test
    Runs openshift-tests / upgrade — the actual pass/fail verdict of the job
    ▼
    What it does Executes openshift-tests run <suite> against the live cluster using the KUBECONFIG written by the install step. For upgrade jobs, it first runs openshift-tests run-upgrade all which triggers the cluster upgrade from UPGRADE_FROM to UPGRADE_TO, then runs post-upgrade conformance. Test results are written as JUnit XML files to the artifacts/junit/ directory. The step exits non-zero if any test fails. Why it exists This is the purpose of the entire job — to verify that OpenShift runs correctly on IBM Z s390x hardware (virtualised via libvirt). A PASSED result here means OCP is Kubernetes-conformant on s390x for this release. Failure means For e2e jobs: Look for "Failing tests:" at the bottom of build-log.txt for the list of failed test names. Download JUnit XML from artifacts/junit/ for CI dashboard integration.
    For upgrade jobs: Check that "Cluster upgrade complete" appears before any test output — if it doesn't, the upgrade itself failed. MonitorTest 503 disruption failures are often CI infra flakes, not real regressions — compare against job history.     Key artifacts
    openshift-e2e-libvirt-test/build-log.txt openshift-e2e-libvirt-test/e2e.log openshift-e2e-libvirt-test/artifacts/junit/*.xml
    POST  ·  Artifact Collection & Cleanup
    📊
    ipi-conf-debug-kdump-gather-logs
    Collects kdump vmcore + extended journal from all nodes
    ▼
    What it does SSHs into each cluster node and collects kdump crash dumps (vmcore files) if any kernel panics occurred during testing. Also pulls extended systemd journal logs. These are uploaded to GCS as artifacts alongside the standard must-gather. Why it exists Kernel panics on IBM Z are rare but when they occur they leave no trace in standard must-gather. The kdump vmcore is the only way to do post-mortem analysis of a kernel crash. Failure means Usually non-fatal (POST steps always run). A failure here means kdump logs couldn't be collected — either the cluster is too degraded to SSH into, or no kdump occurred. This does not affect the overall job result. Key artifacts
    ipi-conf-debug-kdump-gather-logs/build-log.txt
    📦
    gather-must-gather
    oc adm must-gather — full cluster state snapshot for debugging
    ▼
    What it does Runs oc adm must-gather against the cluster, which collects all cluster operator states, pod logs, events, node descriptions, network configs, and storage states into a single tar archive (must-gather.tar). This is the primary debugging artifact for understanding cluster-level failures. Why it exists By the time a human investigates a CI failure, the cluster no longer exists (it gets destroyed in POST). must-gather preserves a snapshot of the cluster state at the moment of failure. Every cluster operator failure, pending pod, degraded node, and error event is captured here. Failure means If must-gather itself fails (FAILED status), the cluster was too degraded to respond to API calls — e.g. the API server was down or all master nodes lost. This is a strong signal that the cluster crashed rather than just having test failures. The must-gather.tar may still be partially written — try downloading it anyway. Key artifacts
    gather-must-gather/build-log.txt must-gather.tar ← download & extract
    🔍
    gather-extra
    Collects additional node-level data — crictl, journalctl, sosreport
    ▼
    What it does Runs additional collection scripts on each node via SSH/oc: journalctl dumps, crictl ps/crictl images for container state, df/free for disk/memory usage, ip route/iptables for network state. For IBM Z specifically it also collects s390x hardware info (lscpu, lsdasd). Why it exists must-gather captures Kubernetes API objects but not low-level OS state. For IBM Z, node-level disk, memory, and hardware info is essential for diagnosing OOM kills, disk pressure, and s390x-specific hardware issues that don't surface in OCP operator logs. Key artifacts
    gather-extra/build-log.txt gather-extra/artifacts/ (node subdirs)
    📝
    gather-audit-logs
    Collects kube-apiserver and openshift-apiserver audit logs
    ▼
    What it does Downloads the Kubernetes API server audit log files from all master nodes. Audit logs record every API call made during the job — create/delete/patch of every resource — with timestamps and the calling user. This is invaluable for debugging RBAC failures, race conditions, and unexpected resource mutations during tests. Why it exists When a test fails because a resource was unexpectedly deleted or mutated, the audit log is the only source of truth for what happened and who/what caused it. Key artifacts
    gather-audit-logs/build-log.txt gather-audit-logs/artifacts/audit-logs/
    ♻️
    upi-libvirt-cleanup-post
    Destroys all VMs, removes DNS records, releases Boskos lease
    ▼
    What it does The mirror of the pre-cleanup step. It connects to the LPAR via qemu+tcp and destroys all VMs (virsh destroy + virsh undefine), removes storage volumes (virsh vol-delete), removes the libvirt network bridge, and deletes all DNS records from the LPAR's dnsmasq. Finally it releases the Boskos lease, freeing the LPAR slot for the next job. Why it exists IBM Z LPARs are shared and finite. Without cleanup the LPAR fills up with stale virsh resources after a few runs. Releasing the Boskos lease is critical — if the lease is not released, the slot stays marked "busy" indefinitely and reduces pool capacity for other jobs. Failure means The most impactful POST failure. If cleanup fails, stale VMs remain on the LPAR. The next job on that slot will fail at install with "storage volume already exists". If the Boskos lease is also not released, the slot count drops. Check upi-libvirt-cleanup-post/build-log.txt for virsh errors. Manual intervention: SSH to the LPAR and run virsh list --all to see stale domains. Key artifacts
    upi-libvirt-cleanup-post/build-log.txt upi-libvirt-cleanup-post/finished.json
